# Security model

This is the long-form companion to the security notes in [README.md](README.md).
It states what Cipherlink defends against, what it explicitly does not,
and the cryptographic reasoning behind both.

The goal is to let a security-minded reader audit the project end-to-end
in a single sitting.

---

## Cryptographic primitive

Cipherlink uses [NaCl `secretbox`](https://nacl.cr.yp.to/secretbox.html)
via [TweetNaCl 1.0.3](https://github.com/dchest/tweetnacl-js).

`secretbox(message, nonce, key)` is:

- **XSalsa20** stream cipher with the 32-byte key and 24-byte nonce.
- **Poly1305** MAC over the resulting ciphertext.

The output includes a 16-byte authenticator. A single bit flipped anywhere
in the ciphertext, the nonce, or the key causes `secretbox.open` to return
`null`. There are no known practical attacks against this construction.

### Key derivation

There is no key derivation. The 32-byte symmetric key is generated by
`nacl.randomBytes(32)` in the browser, which is a thin wrapper around
`crypto.getRandomValues` (CSPRNG). No passphrase, no PBKDF2, no scrypt —
the key never persists.

### Nonce reuse

Each encryption call invokes `nacl.randomBytes(24)` for a fresh nonce.
Reuse of a `(key, nonce)` pair under XSalsa20 would be catastrophic;
random 24-byte nonces make collisions cryptographically negligible.

## Threat model

### 1. Honest-but-curious relay operator

**Defended.** The server holds only `{ ciphertext, nonce, expiresAt,
readsRemaining }`. The key is in the URL fragment, which browsers never
send in HTTP requests — the server cannot decrypt even with full access
to its own request logs.

What the operator *can* see:

- That *a* secret existed.
- Its size (cipher overhead is fixed, so size ≈ plaintext size + 16-byte MAC).
- The TTL and max-reads the creator chose.
- When the creator posted it, when (and from what IP) the recipient
  fetched it.

What is hidden:

- The plaintext.
- The relationship between creator and recipient (no accounts, no auth,
  IP correlation only).

### 2. Passive network observer

**Defended, conditional on TLS.** Cipherlink must be deployed behind
HTTPS. With TLS, the observer sees only encrypted bytes plus IP-level
metadata. Without TLS, ciphertext is still confidential (`secretbox`
holds), but every piece of metadata is exposed.

### 3. Active network attacker (MITM)

**Defended with TLS pinning of the host.** A MITM cannot decrypt without
the URL-fragment key, and the Poly1305 MAC rejects any tampering. They
*could* substitute their own ciphertext if they intercept the response,
but Poly1305 verification fails the second the recipient tries to open
it — they get "could not decrypt", not a falsified plaintext.

### 4. URL leakage (this is the realistic risk)

**Partially defended.** A capability URL is only as safe as its
distribution channel. Specifically:

- **Browser history**: the full URL, including the fragment, is stored
  locally. Anyone with access to the recipient's browser profile can
  recover the secret as long as the server copy still exists. This is
  why one-time-read is the default — once consumed, the local URL is
  worthless even if leaked.
- **Referer header**: Cipherlink ships `<meta name="referrer"
  content="no-referrer">` so links the recipient clicks from the view
  page do not leak the URL.
- **Server access logs**: server-side logs cannot contain the fragment
  by definition of HTTP. Cipherlink also intentionally does not log
  the recipient's IP per fetch.
- **Chat/email middlemen**: anyone who can read the channel you send
  the URL through can read the secret. Use a private channel.

### 5. Compromised browser / XSS

**Best-effort defence.** The URL fragment lives in `window.location.hash`
and is readable by any same-origin script. Mitigations:

- Strict Content-Security-Policy on both pages (`script-src 'self'`,
  no third-party origins).
- No `innerHTML` with untrusted content — viewer uses `textContent`
  exclusively.
- No third-party JavaScript (TweetNaCl is served from `node_modules`).
- The recipient's browser only holds the URL for as long as they
  haven't navigated away.

### 6. Compromised server delivering a backdoored client

**Not defended in code.** Like any web-delivered E2E tool, the server
ships the JavaScript that does the encrypting. A compromised server
could deliver a client that exfiltrates the fragment key. The standard
mitigations (code signing, reproducible builds, browser extensions for
the sensitive client) are out of scope for this demo.

## Server-side validation

The server does not trust client payloads. Every value is regex-checked
before any state mutation:

| Field        | Rule                                                          |
| ------------ | ------------------------------------------------------------- |
| `ciphertext` | Base64, ≥ 16 bytes (Poly1305 MAC size), ≤ 128 KiB.            |
| `nonce`      | Exactly 32 base64 chars → 24 bytes after decoding.            |
| `ttlSeconds` | Clamped to [60, 604800] (1 minute to 7 days).                 |
| `maxReads`   | Clamped to [1, 100].                                          |
| `id` (path)  | Exactly 20–32 chars, matching `[A-Za-z0-9_-]+` (urlsafe b64). |

Body size cap is 256 KiB via `express.json({ limit })`. Per-secret cap
is 128 KiB ciphertext.

The atomic read-consume + record-delete logic lives entirely inside the
`GET /api/secrets/:id` handler — there is no client-side enforcement of
read count.

## Intentional non-goals

- **No DELETE / edit / list endpoints.** Once posted, a secret cannot
  be retracted or modified by the creator. It dies by being read or by
  expiring.
- **No read receipts.** The creator cannot learn whether their secret
  was read. This is a privacy property for the recipient, not a feature
  gap.
- **No persistent storage.** Records live in memory; restart clears
  the store.
- **No passphrase protection.** Could be added (PBKDF2 / Argon2 over a
  user-supplied passphrase, wrap the random key); not in v1.
- **No federation.** Each relay is its own namespace.

## Reporting a vulnerability

Please **do not** open a public issue. Email the maintainer first so a
fix can be coordinated before disclosure. See `/.well-known/security.txt`
for the contact and policy URL.
